## Отступления от плана

- Задачи 6 и 5 выполнены в порядке 6 → 5. Причина: задача 5 требует `getCurrentPlayerImage`, который план создаёт только в задаче 6. Пользователь явно утвердил этот порядок. Задача 6 не опиралась на результат задачи 5.
- В задаче 7 старый экран показывал дату текстом, а интерфейс задачи явно требует формат `ДД.ММ.ГГГГ`. Реализован явный формат `ДД.ММ.ГГГГ`.
- Шаг выкладки из задачи 8 не выполнялся по прямому запрету и по объёму первой части.

## Самостоятельные решения

- Для старых строк базы новые поля в объектах приложения преобразуются в `null` или `false`, чтобы старые записи продолжали открываться.
- Для совместимости со старым экраном настроек оставлен совместимый экспорт списка URL карусели; новый источник — записи `game_photos`.
- После входа со страницы `/admin/login` пользователь возвращается на таймер `/`: страницы `/admin` ещё относятся к следующей части работ.

В обоих случаях: 2 игры, 18 участников, выплаты 23 000 и 19 000 RSD, 412 фото, 43 фото с игрой, 369 значений времени съёмки, 2 текущие картинки игроков с миниатюрами. ## Что должен сделать владелец перед выкладкой

1. Локально и на Vercel заполнить без публикации значений: `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`. Публичные `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` должны быть уже настроены. Служебный ключ не должен иметь префикс `NEXT_PUBLIC_`.
2. Не в день игры выполнить в Supabase SQL Editor сначала `supabase/game_history_migration.sql`.
3. Затем проверить `supabase/game_history_data_migration.sql`: сначала выполнить его в пробной транзакции с откатом и сверить ожидаемые количества, затем после подтверждения выполнить с `COMMIT`.
4. Только после успешного SQL выкладывать код. После выкладки вручную проверить вход на компьютере и телефоне, тестовую игру от старта до завершения и карусель на перерыве. Проверочную игру затем удаляет владелец SQL-запросом, пока пользовательского удаления игры ещё нет.
