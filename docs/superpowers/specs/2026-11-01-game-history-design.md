# История игр: страницы игр и каталог — описание

**Дата:** 2026-11-01
**Статус:** черновик, ждёт утверждения

Пометка **[решение Claude]** означает, что пункт предложил Claude, а пользователь отдельно его не обсуждал. Всё остальное согласовано с пользователем.

## Зачем это нужно

Компания друзей регулярно играет в домашний покер и общается в Telegram-чате: договаривается об играх, обсуждает правила, отправляет фото. Участникам интересно вспоминать прошедшие игры: кто какое место занял, кто сколько выиграл, кто делал ребаи и аддоны. Самое интересное на странице игры — занятые места и фото.

Успех выглядит так: после игры в чат отправляют понятную ссылку, друзья открывают страницу с телефона и смотрят результаты и фото, а админ не вводит результаты вручную и не делает двойную работу с фото.

## Цели

- Отдельная публичная страница для каждой завершённой игры.
- Публичный каталог прошедших игр с общей таблицей игроков за всё время.
- Единая база фото для страниц игр и карусели на паузе.
- Постоянная запись данных игры: суммы выигрыша, время окончания, структура блайндов, показанные картинки.
- Админу всегда понятно, что относится к конкретной прошедшей игре, а что подготовлено для будущих.
- Простой вход в админку.

## Что не входит в эту работу

- Загрузка фото участниками: фото добавляет только админ.
- Личные учётные записи, регистрация, вход через почту или сторонние сервисы.
- Комментарии, реакции, автоматическая публикация в Telegram.
- Полная защита текущих действий во время игры (см. раздел «Вход и защита»).

## Чего нельзя допустить

- Новая картинка игрока меняет то, что показано в прошедшей игре.
- Удаление фото для карусели или действие в настройках незаметно очищает страницы игр.
- Удаление игрока ломает его результаты в прошлых играх или общую таблицу.
- Страницы попадают в поисковики.
- Работающий таймер, мобильная панель или карусель перестают работать из-за изменений.

## Публичные страницы

Открываются без входа у любого, у кого есть ссылка. Все страницы закрыты от индексации поисковиками. Основной сценарий — открытие с телефона по ссылке из Telegram **[решение Claude]**.

### Адреса

- Каталог: `bsptimer.online/games`.
- Игра: `bsptimer.online/games/2026-november-01`.
- Вторая игра того же дня: `bsptimer.online/games/2026-november-01-2`.

Месяц пишется по-английски строчными буквами, день — двумя цифрами. Дата игры — это дата её начала по времени `Europe/Belgrade`, поэтому игра, закончившаяся после полуночи, сохраняет дату начала. Адрес записывается в базу один раз и потом не меняется, даже если соседние игры удалены. **[решение Claude]** для часового пояса (суммы в приложении указаны в RSD) и для неизменности адреса.

### Страница игры

Порядок по значимости:

1. Дата, победитель, банк, число игроков.
2. Таблица результатов: место, игрок, выигрыш, ребаи, аддон.
3. Фото с игры.
4. Картинки вылетевших и победителя, показанные в этой игре.
5. Второстепенно: условия игры и структура блайндов, можно в свёрнутом виде.
6. Ссылка на каталог.

Блоки без данных не показываются. При отправке ссылки в Telegram в чате появляется карточка с датой, победителем и фото.

### Каталог

- Сверху — общая таблица за всё время: игрок, сыграно игр, победы, попадания в призы, суммарный выигрыш, чистый итог. По умолчанию сортировка по суммарному выигрышу, можно переключить на другой столбец.
- Чистый итог = полученный выигрыш − (бай-ин + ребаи × цена ребая + аддон, если был).
- Ниже — список игр, новые сверху. В карточке: дата, победитель, число игроков, банк и одно фото (если есть).
- В таблицу и список попадают все завершённые игры.
- В таблице участвуют все игроки хотя бы с одной такой игрой, даже если их убрали из раздела «Игроки».

## Что записывается по игре

| Что | Когда записывается |
|---|---|
| Структура блайндов и настройки уровней | При старте игры |
| Картинка вылетевшего | В момент вылета. Если вылет отменён, запись убирается |
| Картинка победителя | В момент отметки победителя |
| Суммы выигрыша и время окончания | В момент отметки победителя |
| Адрес страницы | При завершении игры **[решение Claude]** |

Страница появляется автоматически, когда админ завершает игру кнопкой «Завершить игру». Отдельной кнопки публикации нет. Незавершённые игры в каталог не попадают. Игры без отмеченного победителя тоже не показываются **[решение Claude]**.

Механизма скрытия игр нет: завершённая игра с победителем публикуется всегда, сколько бы в ней ни было участников. Если завершить тестовую игру, она тоже появится в каталоге, и админ удаляет её в карточке игры **[решение Claude]**.

Если игрок не имел картинки в момент игры, этот блок для него просто не показывается.

### Старые игры

Выполняется один разовый перенос:

- Суммы выигрыша рассчитываются из сохранённых процентов и взносов по текущей формуле: на каждое место, кроме последнего призового, округление вниз, а остаток банка достаётся последнему призовому месту.
- Время окончания — по времени последнего вылета, с пометкой, что оно примерное.
- Структура блайндов и картинки для старых игр не восстанавливаются, блоки не показываются.
- Настоящих игр две (подтвердил владелец): 2026-05-10 (10 игроков, 3 ребая, 10 аддонов, банк 23 000) и 2026-10-31 (8 игроков, 4 ребая, 7 аддонов, банк 19 000). В день 2026-05-10 в базе есть и тестовые игры, поэтому настоящая определяется по этим значениям, а не только по дате.
- Остальные 132 игры из 134 — тестовые и удаляются из базы безвозвратно вместе с записями участников. Перед удалением делается резервная копия и проверяется, что остаются ровно две игры. Сами игроки не удаляются.
- Записей участников без игрока или без игры нет, у всех участников есть места. Вариант «Удалённый игрок» для старых данных не нужен. Если запись участника была удалена целиком, по базе этого не определить, и признаков такого не найдено.

## Фото

Фото загружаются один раз и показываются в обоих местах: на странице игры и в карусели.

- У каждого фото есть запись в базе с необязательной ссылкой на игру. Имя файла больше не определяет принадлежность к игре.
- Админ загружает фото из карточки конкретной игры.
- Карусель показывает все фото, включая не привязанные к игре. Отдельный выключатель для каждого фото не делаем **[решение Claude]**.
- Дата на фото в карусели берётся из игры. Для фото без игры дата по-прежнему берётся из имени файла.
- Кнопка удаления всех фото заменяется удалением отдельных фото. Перед удалением показывается, что фото исчезнет и со страницы игры, и из карусели.
- Фото можно перенести в другую игру или убрать из игры.

### Перенос существующих фото

В текущем хранилище 412 фото общим объёмом 65 МБ, дата есть в имени каждого файла (пример: `photo_87@06-02-2023_01-22-09.jpg`). Снимки охватывают период с ноября 2022 года, а игры в базе есть только с апреля 2026 года. Совпадает по дате только один день с играми: 2026-05-10, 43 фото.

Для всех файлов создаются записи:

- 43 фото за 2026-05-10 привязываются к настоящей игре этого дня **[решение Claude]**;
- остальные 369 фото образуют начальный пул «Без игры» и остаются в карусели;
- дата и время из имени файла сохраняются в записи и дальше не зависят от имени.

Сами файлы не перемещаются и не переименовываются.

Пул не пополняется: после запуска новые фото загружаются только через карточку игры, а старая загрузка в настройках убирается. Страницы для встреч до апреля 2026 года не делаем, потому что их результатов в базе нет.

## Картинки игроков

Для админа есть два ясно разделённых места:

- **Раздел «Игроки»** — картинки для будущих игр, с подписью: «Будет показана в следующих играх, прошедшие не изменятся».
- **Карточка игры** — картинки, сохранённые за этой игрой, с понятным указанием, что это снимок данной игры. Админ может заменить такую картинку, и это действует только на эту игру **[решение Claude]**.

Каждая новая загрузка хранится как отдельный файл, а игра ссылается на конкретный файл. Удаление картинки в разделе «Игроки» не удаляет файл, который использует прошедшая игра **[решение Claude]**.

## Админка

Новый раздел «Игры»:

- Список всех завершённых игр и группа «Без игры» для непривязанных фото. По умолчанию при загрузке открыта самая свежая игра.
- Карточка игры: ссылка на публичную страницу, фото, сохранённые картинки, правка результатов, удаление игры.
- Удаление игры безвозвратно и требует подтверждения. Её фото не удаляются, а переходят в «Без игры» и остаются в карусели **[решение Claude]**.
- «Без игры»: просмотр пула, удаление отдельного фото и перенос его в игру.
- Правка результатов: можно исправить места, число ребаев и наличие аддона. Суммы выигрыша пересчитываются автоматически, и общая таблица обновляется.

## Удаление игроков

Удаление игрока в разделе «Игроки» больше не удаляет запись из базы, а только скрывает игрока из выбора для новых игр. Его результаты, имя и позиция в общей таблице сохраняются.

## Вход и защита

Один общий пароль, без почты и учётных записей. Пароль вводится один раз на устройстве, устройство запоминается примерно на год.

Закрыты паролем: настройки и все кнопки управления игрой на компьютере и в мобильной панели, раздел «Игры». Открыты без пароля: просмотр таймера и публичные страницы.

Уровни защиты:

- **Защищено на сервере:** загрузка, перенос и удаление фото; загрузка и удаление картинок игроков; правка результатов; удаление игры; завершение игры и запись итогов.
- **Защищено только на экране в первой версии:** действия во время идущей игры (ребаи, аддоны, вылеты, рассадка, управление таймером), потому что они продолжают писать в базу напрямую из браузера. Пользователь принял этот риск для домашней игры.
- **Завершённые игры:** правила базы запрещают менять их через публичный ключ, иначе защита правки результатов не имела бы смысла.

## Технические решения и ограничения

- Стек: существующий Next.js + Supabase + Vercel, деплой при пуше в `main`.
- Вход: `POST /api/admin/login` проверяет пароль и ставит подписанный cookie (`httpOnly`). Секреты `ADMIN_PASSWORD` и подпись cookie хранятся в переменных окружения на Vercel, NextAuth и таблица пользователей не нужны.
- Серверные операции используют служебный ключ Supabase, который не попадает в браузер.
- Vercel ограничивает размер запроса 4,5 МБ, поэтому фото загружаются напрямую в хранилище по временной подписанной ссылке, которую выдаёт сервер после проверки входа.
- Фото нужно уменьшать при загрузке и создавать миниатюры (подход уже есть в `lib/supabase/imageVariants.ts`), чтобы не выйти за лимиты Supabase; страницы показывают миниатюры.
- Стили: Tailwind, тема через `dark:`, без inline-стилей.
- Страницы с данными из базы не должны кэшироваться навсегда при сборке: обновление результатов и фото отображается без нового деплоя.
- Нужно закрыть прямую запись в хранилище фото `slideshow` для публичного ключа и убрать ограничение списка в 1000 файлов для карусели.
- Текущие файлы по теме: `lib/supabase/sessions.ts`, `lib/supabase/slideshow.ts`, `lib/supabase/imageVariants.ts`, `lib/supabase/players.ts`, `context/GameContext.tsx`, `components/PokerTimer.tsx`, `components/SlideshowOverlay.tsx`, `components/SettingsScreen.tsx`, `components/MobileAdminPanel.tsx`.
- Изменения базы оформляются SQL-файлами в `supabase/`, как существующие миграции. Реальные правила доступа рабочей базы перед изменениями нужно сверить: они не проверялись.
- Служебного ключа в проекте нет, а миграции выполняются вручную в SQL Editor на сайте Supabase. Каждая миграция идёт с готовой инструкцией и проверкой для владельца проекта. Служебный ключ владелец сам добавляет на Vercel **[решение Claude]**.
- Отдельную тестовую базу не заводим. Перед миграциями владелец делает резервную копию, выкладка проходит не в день игры, изменения базы выполняются раньше зависящего от них кода, а запрет записи публичным ключом включается последним, после проверки таймера и мобильной панели **[решение Claude]**.
- Версия: в `CLAUDE.md` указана 5.2, а в `CHANGELOG` уже есть 6.0. Новая запись идёт от 6.x, а строка в `CLAUDE.md` исправляется.

Цвета, типографика, отступы, тексты и состояния воссоздаются точно, но средствами Tailwind. Папку нельзя удалять до окончания работ. В репозиторий она не копируется, потому что содержит картинки реальных людей.

Если README расходится с этим описанием или кодом проекта, действует следующее **[решение Claude]**:

| В README | Как делаем | Почему |
|---|---|---|
| Выигрыш округляется до сотен | `calcGameStats`, как сейчас | README сам требует его использовать, а суммы должны совпадать с показанными на таймере |
| Таблица `session_images` с копиями файлов при завершении игры | `player_images` со ссылками, запись в момент показа | Нет дублирования файлов, сохраняется именно показанная картинка |
| Защита через middleware | Проверка в маршрутах и серверных страницах | Не нужен дополнительный слой, а записи всё равно проверяются на сервере |
| Частичное кэширование страниц (ISR) | Без кэширования (`force-dynamic`) | Правила проекта, правки видны сразу |
| Supabase Image Transformations | Миниатюры создаются в браузере при загрузке | Так уже работают картинки игроков; утверждение README о трансформациях неверно |
| Все существующие фото без игры | 43 фото за 2026-05-10 привязываются к игре | Решение из этого описания |
| Строка админки «нет победителя» | Не нужна | Завершить игру можно только после отметки победителя |
| «с 2022 года» в шапке каталога | Убираем | Таблица считает игры только с 2026 года, надпись вводит в заблуждение |
| `title`, `sort` у игр и фото | Не добавляем | Не используются в экранах |

Новое из дизайна, принимаем **[решение Claude]**:

- У фото появляются `width`, `height` и `taken_at` вместо только даты: страница не прыгает при загрузке снимков, а просмотр идёт по времени съёмки.
- В админке есть кнопка «Выйти».
- На странице недавней игры (меньше 7 дней) без фото показывается плашка «Фото с вечера появятся позже».
- Пути админки: `/admin/login`, `/admin`, `/admin/games/[slug]`, `/admin/no-game`, `/admin/players`.
- Раздел «Игроки» переезжает в админку, а вкладка в настройках таймера показывает тот же компонент, чтобы во время подготовки игры не уходить со страницы.
- Сохранённую картинку в карточке игры можно только заменить. Отдельное удаление в дизайне не предусмотрено и убрано.

Порядок работ: сначала база, вход и перенос данных, затем экраны.
